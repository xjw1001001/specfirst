# ADR-002: Our own R result engine, and the choices of real-2

Reworded in real-3a (2026-11-17) after the review of real-2: findings F8
(four sentences that said more than their evidence), F10 ("every quantile
definition" means the two of the registry), F2 and F3 (the proof of the
median of height, and the Fisher test in R, have changed since). No decision
is changed. The changed sentences are marked "(real-3a)".

Status: decided in real-2, 2026-11-11. PLAN.md hands decision 1 to this work
package (sections 7.1 and 13.3, E12). Decisions 2 to 8 are the executor's
choices where the plan is silent; they stand unless the owner objects.
PLAN.md, `standard/schemas/` and `env/` are not changed.

Four points are for the owner to confirm, because they go beyond what the
plan says in words:

- Decision 1 does not build the R engine "on cards and cardx", as section
  7.1 words it. It uses the functions of R's `stats` package that cardx
  itself calls.
- Decision 5 adds to the kit layout of section 8, as ADR-001 item 3 did.
- Decision 6 finds a 25th difference between CDISC's example and the pilot
  data. Evidence E3 counts 24. All 25 are classed `reference_error`; the
  class of each is the executor's reading.
- Decision 2 names a change of `env/` that would make the R engine simpler.
  It is not made.

## Context

real-2 turns the spike `evidence/ars_spike.py` into two result engines that
must agree (rule R11), a method registry that fixes what ARS leaves open
(E4), and a check that every result of a reference is reproduced or
classified (section 4.8). Rule R2 asks to try siera before writing an R
engine.

## Decisions

1. The R engine is our own: `r/specfirstr/`. It does not wrap siera.

   `evidence/adr002_siera_trial.sh` is the trial, with siera 0.5.6, cards
   0.9.0 and cardx 0.3.4 from the locked library; its output is
   `evidence/adr002_siera_trial.out`.

   | Trial | Result |
   | --- | --- |
   | T1: siera on CDISC's example, as fetched | 5 scripts, and no line in them that computes anything. siera takes the arithmetic of a method from R code that the ARS file must carry in `codeTemplate`. CDISC's example has no such code: 31 of 31 analyses are skipped ("does not have any AnalysisMethodCode entries"), and the SAS templates of 6 analyses name value sources siera does not know. |
   | T2: siera on its own variant of the example | The pinned repository has a variant with R code in every method. It has 23 of the 31 analyses: the tables by organ class and preferred term and all six Fisher tests are left out. Four analyses are given another method. For 8 analyses the code template names a value source that the CRAN build of 0.5.6 does not know. siera's Fisher template gives an odds ratio and its interval, not a p-value: that is true of the pinned files (`inst/method-library/06_fishers_exact`, read by the reviewer of real-2), and the recorded output does not show it; its line "a Fisher test with a p-value among them: False" only tests whether a method of the variant has "fisher" in its name. (real-3a) |
   | T3: the scripts of T2 on the pilot ADaM | The scripts attach readr and parameters, which are not among the 99 locked packages; for the trial only, the data were read with base R. The demographics script stops at the first analysis of variance: `cardx::ard_stats_aov` needs broom.helpers and parameters. From the other scripts, 2,029 of the 3,735 embedded results are equal, 1,693 are not computed, and 13 percents are proportions (a factor of 100). |
   | T4: cards and cardx for the registry's methods | `ard_stats_aov` fails as above; `ard_stats_oneway_test`, `ard_stats_chisq_test` and `ard_stats_fisher_test` run. `cards::ard_summary` computes quartiles by quantile type 2 (the SAS default) with no option in siera's template; `ard_tabulate` gives a proportion. 200 Fisher tests take 2.4 s through cardx and 0.06 s through `stats::fisher.test`; the tables by preferred term need about 400. |

   Why not siera:

   - It is a generator of one R script per output, not an engine that
     reads an ARS file and a registry. The method lives as R code inside
     the ARS file. The plan wants the opposite: methods in the registry,
     "never through code inside a spec" (section 15), and the same ARS file
     for both engines.
   - It cannot run the reference of this work package (T1), and its own
     variant covers 2,029 of 3,735 results (T3).
   - Its scripts need packages outside the lock, and carry the time they
     were generated (rule R4).

   Why not cards and cardx at run time, although section 7.1 names them:

   - For the six methods of registry v0 they add no method. cardx's tests
     are wrappers of `stats::chisq.test`, `stats::fisher.test` and
     `stats::oneway.test`. Our engine calls `chisq.test` and `fisher.test`
     directly and takes the F test from `anova(lm())`, not from the
     `oneway.test` that cardx wraps. (real-3a)
     The descriptive statistics need the registry's numbered semantics
     (which quantile definition, percent or proportion), so every default
     of cards would have to be overridden.
   - The wrappers cost a factor of 40 where a table has hundreds of tests
     (T4: 2.4 s against 0.06 s for 200 Fisher tests). One of them,
     `cardx::ard_stats_aov`, needs two packages outside the lock;
     `ard_stats_oneway_test(var.equal = TRUE)`, which is the same F test,
     runs with the locked library, and so do the chi-square and the Fisher
     wrapper (T4). So the lock is no reason against cardx; the reasons are
     that the wrappers add no method, cost time, and that the descriptive
     defaults would have to be overridden. (real-3a)
   - What rule R11 asks for is a second implementation that does not share
     code with the first. The Python methods are written from the
     definitions (the Fisher test by its own enumeration); the R methods
     use `stats::quantile` types 2 and 7, `chisq.test`, `fisher.test` and
     the F test of `anova(lm())`. Since real-3a `fisher.test` is used for a
     2 x 2 table only: for a larger table it allows a wider excess than
     the registry (statement 8 of `test.fisher.exact`), so the R
     implementation sums over every table itself, as the Python one does.
     (real-3a)

   cards and cardx stay in the lock. If the owner wants the R engine to go
   through them, the change is in `r/specfirstr/R/methods.R` alone.

   The engine uses base R (`stats`, `tools`, `utils`) and jsonlite (MIT).
   It is sourced from its folder, not installed: `specfirst doctor` counts a
   package outside `env/r-packages.lock` as drift, and the R library is
   shared by every checkout of this machine.

2. Data are handed to the R engine as JSON; `env/` is not changed. The
   locked R library has no Parquet reader, and no YAML reader. Adding one
   (arrow, nanoparquet, yaml) changes `env/`, and because all checkouts
   share one R library and `doctor` fails on any package the lock of its
   own checkout does not name, every other track would fail its gate until
   it had merged the new lock. That needs the owner and the other tracks;
   it is not done here.

   Instead `specfirst.machine.rengine` writes, per dataset, the columns the
   analyses read (23 for the example) as one JSON file, numbers as the
   shortest decimal that reads back as the same double. The R engine
   reports the SHA-256 of every column as it read it, and the build fails
   unless each equals what the Python side computes from the Parquet data.
   The registry reaches R as `standard/methods/registry.json`, generated
   from the YAML entries and checked for staleness by a test and the gate.

3. Method registry v0: seven entries in `standard/methods/`, one YAML file
   each (format in the README there). Each has numbered semantics, options
   with defaults, test vectors in `tests/methods/` and cross-references to
   CDISC's example and to siera's templates. The AC/DC cross-reference is
   null until M2 (E11).

   - The vectors' expected values are not taken from the engines:
     `tests/methods/oracle.py` computes them again with fractions and
     closed forms, and a test compares.
   - Fisher's exact test sums over every table for any size (E27). Our
     enumeration and R's `fisher.test` agree on the eight vectors larger
     than 2 x 2 to a relative 1e-12 (gate check "method vectors").
   - The display rule "round half away from zero" has a Python
     implementation only: a display rule is applied once, where the grid is
     built (section 7.2).
   - The entries are checked by code. A schema for them in
     `standard/schemas/` (section 12 lists one) needs an ADR the owner
     approves; it is left for when std-1's catalog schema has passed N1.

4. How an analysis is run is written down as rules I1 to I15, and how an
   ARS operation is bound to the registry as rules B1 to B3
   (`standard/methods/README.md`). Both engines follow them. The choices
   that change numbers:

   - A missing value fails EQ, IN and every ordered comparison, and passes
     NE and NOTIN (I3). SAS orders a missing number below every number; we
     do not.
   - A group that is defined always gives results, a data-driven group
     only when it occurs, and several data-driven groupings give the
     combinations that occur (I8 to I10). On the example this gives 4,238
     rows: the 3,734 results with a value that CDISC embeds, and 504 more
     (the Fisher tests for every organ class and preferred term, where the
     example embeds one each, and the baseline cells of change from
     baseline, which have no record).
   - The denominator of a test of occurrence (the example's Fisher tests)
     is the analysis set within the subject part of the data subset (I13).
   - A method option that ARS has no place for is given per registry
     method by the kit, or by the analysis in `programmingCode` with the
     context `specfirst method registry` (the convention of std-1).

5. ARD and kit. The ARD schema v0 is used unchanged. A row's `id` is
   `ard:<analysis>/<operation>/<group parts>`; rows are sorted by it and
   written as canonical JSON lines. Additions to the kit layout of section
   8, in the way of ADR-001 item 3:

   | Path | What |
   | --- | --- |
   | `kit.yaml`: `results` | per reporting event: the ARS file, the schema of the ARS model, the subject key, the binding |
   | `kit.yaml`: `build.exceptions` | our own file with the classified differences |
   | `gold/spec/ars/` | pinned: CDISC's example and the JSON Schema generated from the ARS model, both from the source `ars` |
   | `gold/ard/<id>.jsonl` | built: the ARD of the Python engine, the gold ARD |
   | `gold/ard/<id>.r.jsonl` | built: the ARD of the R engine |
   | `gold/ars/<id>.json` | built: the reporting event with our results in place of the embedded ones, raw values only |
   | `kits/<kit>/gold/exceptions.yaml` | in git: a kit folder of tier B or C may now hold this file besides `kit.yaml` and `README.md` |

   The ARS example is fetched and never committed. Every ARS file, pinned
   or built, is validated against the pinned schema. A build runs both
   engines, so a kit with a reporting event needs R to build. P1 covers
   the three built files.

6. P2 for results (`specfirst.machine.results`). The reference drops
   trailing zeros from its raw values ("70" for 70.0, "1" for a p-value of
   1), so "the reference's printed precision" (section 4.6) is compared in
   two steps: as printed, which is the comparison of E2 and what
   "reproduced" counts; and at the precision of the operation's
   `resultPattern` where that shows more decimals. Both allow a relative
   1e-9. A result that passes the first step only is a difference.

   - Both engines reproduce 3,711 of the 3,735 embedded results as printed,
     the count of E2.
   - 25 results need a class, not the 24 of E3. The 25th is the first
     quartile of age in the high dose arm: the example has 70 (formatted
     70.0), the pilot ADSL gives 70.5 by the SAS default (the mean of the
     21st and 22nd of 84 ages, 70 and 71) and 70.75 by R's. E3 counted it
     as reproduced, because 70.5 is within half a unit of "70". A planted
     defect showed the hole: a dropped data subset passed where the
     reference prints a p-value as "1".
   - The same holds for E4: with R's quantile definition 49 fewer results
     are reproduced as printed (3,662, as E4 says), and 97 differ at the
     precision of their pattern.
   - `kits/cdiscpilot01/gold/exceptions.yaml` lists the 25, each with a
     proof the check verifies on every run: 22 are our value of the other
     active arm (`value_of_other_result`); the median of height lies
     between sorted values that are all 162.6, so that every definition of
     a median gives our value (`between_equal_values`); the quartile of age
     is the embedded value under neither of the two quantile definitions of
     the registry while the rest of its cell is reproduced
     (`no_alternative`); the empty p-value has no records behind it
     (`no_records`). All are classed `reference_error`. (real-3a: in real-2
     the proof of the median was `same_under_every` on the quantile
     definition. The two definitions of the registry never differ on a
     median, so that proof said nothing; the check now refuses it.)

7. The Python engine takes 0.4 seconds for the 31 analyses (the spike:
   about 3 minutes; the target: under 10 seconds), the R engine 2 seconds.
   A test in the gate fails above 10 seconds.

8. Planted defects (rule R5) are run on the real example, the real pilot
   data and both real engines, and judged by the functions the gate calls.
   What the pilot data cannot show is reported, not counted as caught: the
   safety set and the intent-to-treat set hold the same 254 subjects, and
   of the 18 analyses with a data subset, dropping it changes no result
   for one and changes only results the reference does not list for two.

## Consequences

- `specfirst build` of a kit with a reporting event needs R. CI has no R:
  there the tests that need it are skipped; the gate fails if one is.
- The checks see what a reference embeds. Our 504 results beyond the
  example are covered by the agreement of the two engines, not by P2.
- For std-1: its convention "Method registry: <id>" in a method's
  description is rule B2 and works as it is. Registry v0 has no
  `count.records`; a compiled ARS file that uses `Mth_EventCount` cannot
  run until an entry exists. Data-driven treatment groupings work for
  descriptive results and for tests (I9, I12).
- For real-3: `specfirst.machine.ars.reads` gives the `reads` edges of an
  analysis. Comparing cell text with the example's formatted values will
  meet the 25 differences again; the grid has no ARD row for a result the
  engines do not give.
- For the owner: the classes of the 25 differences, and whether E3 and E4
  of PLAN.md should say 25 and 97 at the next revision of the plan.
