# ADR-001: The yamaa wheel with our own runner, and the choices of real-1

Status: decided in real-1, 2026-11-11. PLAN.md hands decision 1 to this
work package (section 13.3, E19). Decisions 2 to 7 are the executor's
choices where the plan is silent; they stand unless the owner objects.
Item 3 adds to the kit layout of PLAN.md section 8, which is a design an
ADR may improve; PLAN.md itself is not changed. The owner approved the
additions of item 3 on 2026-11-11 (finding F12 of the review of real-1).
The approval covers item 3 only: decisions 2 and 4 to 7 stand as before,
unless the owner objects.

## Context

Pilot 7 builds the ten CDISCPILOT01 ADaM datasets with yamaa and compares
them with the reference. Its own runner refuses a wheel: it requires yamaa
installed from git revision `c039509082b545fe913c00d1686426c3d245778c`
(tag yamaa-v0.7.0), which needs a Rust 1.99.1 toolchain to build (E19). E1
showed that the PyPI wheel of the same version rebuilds all ten datasets
with 0 mismatches. real-1 had to choose, and to turn the spike into the
first part of the machine: a kit, a runner, canonical writers, P1 and P2 as
tests, and the SDTM to ADaM part of the graph.

## Decisions

1. Engine: the wheel. yamaa 0.7.0 comes from PyPI, pinned by version in
   `pyproject.toml` and by SHA-256 in `env/requirements.lock`, and installed
   with `--require-hashes --only-binary=:all:`. No source build, no Rust
   toolchain. Evidence, rerun by `specfirst gate real-1`:

   | Test | What it shows |
   | --- | --- |
   | A1-resolve | The wheel composes each of the 10 pilot specifications to exactly the snapshot Pilot 7 committed (`spec/yamaa/resolved/*.inspection.json`), which Pilot 7's runner made with the engine built from the pinned revision. 10 of 10 are equal as canonical JSON, origins included. The test also checks that the snapshots name the revision Pilot 7's requirements file pins. |
   | P2 | The datasets the wheel builds equal the reference: 9,119,605 cells, 0 mismatches. |

   What is given up: Pilot 7's guarantee that the engine is the reviewed
   revision, checked at run time. What replaces it: the wheel's hash in the
   lock file, the two tests above, and the engine version in every kit
   manifest, which `specfirst build` compares with the installed one before
   it runs. A1 and P2 cover the ten pilot specifications, not every
   construct of the language.

2. Runner: every input in memory. `specfirst.machine.runner` resolves each
   specification of the project, in yamaa's run order, and calls
   `spec.run(inputs=...)`. An input that another specification of the
   project produces is that specification's output of this run; any other
   input is the SDTM file of the same name in the kit's `inputs/data/sdtm/`.
   `save()` is never called, so nothing is written next to the
   specifications or into the fetch cache. The specifications are used
   byte for byte as Pilot 7 wrote them.

   The alternative was yamaa's own project run on a staged copy of Pilot 7's
   folder layout, as the E1 spike did. It needs the data at the paths the
   specifications name, which would put inputs under `gold/`. Test A2-runner
   shows the two give the same tables, values and types, for all ten
   datasets.

3. Kit layout. A kit folder in git holds `kit.yaml` and a README only. The
   manifest names all 64 files by source, path and SHA-256; `specfirst kit
   assemble` copies them from the fetch cache and refuses a file whose hash
   is not the pinned one. Additions to section 8, each under `gold/`:

   | Path | Why |
   | --- | --- |
   | `gold/reference/adam/` | Section 8 has `gold/data/adam/` only. For a real study the reference (what the study delivered) and our build are two things, and P2 compares them. The build goes to `gold/data/adam/`. |
   | `gold/claims/` | Pilot 7's reviewed claims describe the rules behind the reference, so they are gold. |
   | `gold/resolved/` | The composed specifications with the origin of every element: the input of the graph builder, and part of P1. |
   | `gold/build.json` | The SHA-256 of every built file: what P1 compares. |
   | `gold/spec/<paths of Pilot 7>` | Pilot 7's specifications keep their relative paths, because a child names its parent by one. |

   The ADaM Define-XML is under `inputs/docs/`: the plan lists the Define-XML
   files among the inputs, and Pilot 7's claims cite it as a document. Of
   the manifest fields section 8 names, a tier C kit has no archetype,
   split or generator version; the identifiability summary comes with
   std-2. The
   manifest format is checked by code (`specfirst.kit`), not yet by a schema
   in `standard/schemas/`: adding one there needs an ADR the owner approves,
   and gen-2 will know better what a generated kit needs.

4. Canonical ADaM file. Parquet written by the pinned pyarrow with every
   writer option fixed, after dropping schema and field metadata, combining
   chunks and mapping large strings and dictionary columns to plain ones
   (`specfirst.machine.canonical`). Row and column order are the engine's:
   the specification's `output.order_by` and `output.columns`. The hash of a
   dataset is the SHA-256 of that file, so it holds under the pinned pyarrow
   only; the lock file pins it. P1 compares two builds, each made in a new
   process and in its own folder with its own copy of the kit, so that a
   byte that depends on the process or on the folder differs. Both folders
   are in one checkout and both builds run in one environment: a byte that
   depends on the root of the checkout or on the environment would be the
   same in both and would pass. The delivered code has no such byte: the
   `build.json` of a clean clone under `/tmp` and of a build in the
   worktree on the Windows drive were byte for byte the same (report and
   review of real-1, S5). That comparison was made by hand. The gate cannot
   make it against a recorded hash, because the hash changes with every
   change of the graph.

5. P2 compares values by logical kind. The 10 reference files store text as
   Arrow `large_string` (pandas wrote them); yamaa returns `string`. That is
   the whole of the type differences E1 counted: 221 columns, 14 to 38 per
   dataset, the same values in two storage types. P2 does not count them
   and prints them. A column whose kind differs (text against number, or a
   time stamp in one time zone against another zone or none) mismatches in
   every cell that is not missing on both sides. The comparison follows
   `evidence/compare_adam.py` with three holes closed: NaN against a number
   is a mismatch, and an extra column or another column order fails the
   comparison. The tolerance of 1e-10 is absolute. PLAN.md section 4.6 says
   "numeric tolerance 1e-10" and no more; the E1 spike read it as absolute,
   and P2 keeps that reading. P2 prints how many numeric cells are equal
   within the tolerance but not exactly, with the largest difference, so
   that the reader sees how much rests on it.

6. Graph. One node per ADaM output column and per SDTM column read; helper
   columns, lookups (yamaa's intermediates) and row templates are passed
   through. An SDTM node's source is its `ItemDef` in the SDTM Define-XML.
   What a `derives_from` edge means, and what it does not:

   - It says what a column's rule reads, not which rows contributed. A
     value the rule computes with and a column that only selects or orders
     rows (the filter of a row template or of the specification; the key,
     filter and order of a lookup) both give an edge, and the v0 edge
     schema has no field to tell them apart. `coverage.json` records per
     column whether the rule itself reads a column (`value`); a filter on
     rows is not part of the rule. In the pilot 16 of the 415 columns have
     a rule that reads no column: 14 of them reach SDTM only through the
     filter of their row template, and 2 are literals on unfiltered rows.
   - There is one edge per pair of columns, so it names one place: a rule
     before a filter on rows or the declaration of a lookup, then the
     nearest on the way, then the lowest file and line. A column taken
     through a lookup is cited at the rule that names it, whether the
     lookup reads an input or the dataset itself. A join key is cited at
     the rule that causes the join, though the key is named in the
     specification's `input`; a reader who opens that line finds the join,
     not the key column.
   - The hash of an ADaM node covers the column's own rule and every helper
     column, lookup and row template the rule passes through, so that a
     changed helper changes the hash of the columns that read it.
   - A column that reaches no column is `literal` in `coverage.json`, with
     the declared inputs whose rows it sits on; the graph has no node for a
     literal or for a dataset. A column is complete only if every column it
     reaches is: a gap is passed on to the columns that read it.

   Pilot 7's claims become `cites` edges from the ADaM column to
   `doc:<id>#<anchor>`: judged, imported, `quote_verified` false,
   `approved_by` null. One edge stands for all citations of one span by one
   column (the pilot's 913 citations of kit documents give 706 edges), and
   it carries the line of the claim, not of a quote; real-3, which checks
   quotes, will need more than one flag per edge. Citations of programs
   are not imported, because programs are not kit documents.

   The trace check proves that the graph files fit the schema, agree with
   each other and record no gap that the kit does not list. It cannot see a
   reference the dependency analysis missed. For the pilot that is covered
   from two other sides: A3 (the analysis equals Pilot 7's) and A4 (with
   every SDTM column that has no node changed, the engine builds the same
   ADaM; a column with more than one value is rolled by one row, a column
   with one value is emptied, a column that is all missing is filled).

7. Column dependencies: adapted from Pilot 7, not written anew (rule R2,
   section 7.1). `specfirst.machine.lineage` is Pilot 7's `references.py`
   and `lineage.py` (MIT), changed to report where each column is read.
   Test A3-lineage runs Pilot 7's own code from the cache and compares: the
   dependencies are equal for all ten specifications. Calling Pilot 7's
   code at build time was the alternative; it would tie every kit's build
   to the layout of another repository. One more function is adapted from
   Pilot 7: `_relocate` in the runner follows `relocate` of
   `resolved_specs.py`. `third_party/SOURCES.md` records both files, with
   the license text in `third_party/licenses/`; test A5-adapted compares
   our Python files with those of the cached sources to find adapted code
   that nobody recorded.

## Consequences

- `specfirst gate real-1` needs the fetch cache but no network and no
  compiler.
- A new yamaa version is a deliberate change: lock file, kit manifests, and
  the gate again.
- P1 is tested on two builds with the Python host. yamaa's R host is not in
  the environment of PLAN.md section 13.2, so the comparison across the two
  hosts that section 4.6 mentions is not made.
- The quotes of the imported claims are not checked against the documents
  yet. real-3 completes the graph to the documents and owns that check.
