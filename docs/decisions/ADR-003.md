# ADR-003: Layout spec v0 is our own format, and the choices of real-3a

Status: decided in real-3a, 2026-11-17. PLAN.md hands decision 1 to real-3
(sections 7.1 and 13.3: "own layout format or tfrmt JSON"); ADR-005 moves it
into the part real-3a. Decisions 2 to 7 are the executor's choices where
the plan is silent; they stand unless the owner objects. PLAN.md,
`standard/schemas/` and `env/` are not changed.

Corrected on the same day, after the review
(`docs/reports/real-3a.review.md`, finding F1). The first version said that
the table shell the example names is not in its repository. It is. The
fifth point below, the context, decision 5, the list of what is left and
the consequences are changed for it, and the section "The example's table
shell" is new. No decision is changed.

Five points are for the owner, because they go beyond what the plan says
in words:

- Decision 1 rests on reading tfrmt, not on running it. tfrmt is not among
  the locked R packages, and on 2026-11-17 the Linux environment of this
  machine reached no network, so no trial library could be installed. What
  was read is public and pinned by commit below. One claim was run without
  tfrmt: the rounding (T1).
- Decision 4 shows a count under a column header as a cell of a row with the
  section `@header`. Schema version 0 of the grid has no place for a result
  in a column. A field for it would be cleaner; that is a schema change and
  is not made.
- Decision 3 adds the registry entry `display.pattern`. Three of its
  statements are read off the formatted values of CDISC's example; no public
  standard states them.
- Decision 7 adds to the kit layout of PLAN.md section 8, as ADR-001 and
  ADR-002 did: `gold/layout/` in the kit folder and in the build, and
  `outputs` in `kit.yaml`.
- Decision 5: the check of grid text compares per result, with the
  formatted values of the example's ARS file. It does not see in which
  order the parts of a cell stand. The example's table shell shows that,
  and it is in the pinned repository; nothing holds the grid against it
  yet, and the grid lacks one line of the row axis that the shell has.

## Context

The layout spec holds what ARS does not (section 7.4): the column axis, the
row axis, the cell templates that combine operations, the decimals, and how
a missing value is shown. The grid builder turns a layout and an ARD into
`grid.json`, where every cell has its text and the IDs of the ARD rows
behind it. A mock shell is the same grid without results.

What existed before real-3a:

- Four layout templates of the house standard, "layout draft 0", written by
  std-1 before any builder read them (ADR-004, decision 6: "real-3 fixes the
  layout format in ADR-003; std-2 aligns the house layout templates").
- The grid schema, version 0, from base-0.
- CDISC's ARS example. Its outputs carry the titles, footnotes and the
  header of the row labels (`displaySections`), its analyses carry labels,
  its operations carry a `resultPattern` such as "( XX.X)", and 3,734 of its
  3,735 results carry a `formattedValue`. The ARS file does not say which
  analysis is which row, which results share a cell, or what a pattern
  means exactly. Each output names a table shell as a reference document;
  the shells are files next to the example in the pinned repository (see
  "The example's table shell").

Rule R2 asks to look at tfrmt before a layout format is written.

## Evidence

### tfrmt, read

Repository `GSK-Biostatistics/tfrmt`, commit
`8feb95a3af25a2aeac6ae402c676dc0d360eec7b` (2026-11-06), version
0.4.0.9000, license Apache-2.0 (`DESCRIPTION`). Read on 2026-11-17 from the
public repository: `DESCRIPTION`, `NAMESPACE`, `R/JSON.R`,
`R/apply_frmt_methods.R`, `R/apply_tfrmt.R`. Nothing of it is imported,
copied or installed, and it is not a pinned source of this repository.

| Question | What the source says |
| --- | --- |
| What it needs | R, and the packages it imports. Two of the fifteen are not among the 99 locked packages: gt (1.1.0 or later) and forcats; gt brings its own dependencies. |
| What it reads | A data frame in long form whose columns the tfrmt object names: `group`, `label`, `param`, `value`, `column` (`validate_cols_match` in `R/apply_tfrmt.R`). Row labels and column labels are values of the data. It knows no analysis, operation or group ID of ARS. |
| What its JSON is | `tfrmt_to_json` writes the tfrmt object; `json_to_tfrmt` reads it. The file has no schema and no version field. Expressions are R code as text (`rlang::as_label`, `deparse`), and they are turned into R code again when the file is read (`str2lang`, `rlang::parse_expr`, `stats::as.formula`). |
| How it shows a number | `format(round(vals, dig), decimal.mark = ".", nsmall = dig)` in `apply_frmt.frmt`: R's own `round`. The digits come from the x after the point of the format ("xx.x"). There is no option for the rounding rule. |
| What it gives back | A gt table (`print_to_gt`). The internal `apply_tfrmt` (`@noRd`, not exported) gives a wide table of texts. Neither keeps, for a cell, which rows of the input were shown in it. |
| What it has that we need later | A mock from the format alone (`print_mock_gt`, `make_mock_data`); a combined cell (`frmt_combine("{n} {pct}")`); the count of a column in its header (`big_n_structure`); plans for row groups, column order and spanners, footnotes and pages. |

### T1: R's round on the results of the pilot

`evidence/adr003_rounding.sh`, recorded output
`evidence/adr003_rounding.out`. It runs the one expression above, in base R
4.6.2, on every result of the pilot that the example shows with decimals,
and compares the text with the registry's
`display.round.half_away_from_zero` and with the example's formatted value.

```text
results of the pilot with a value and a pattern with decimals: 2537 of 4238
values that lie exactly on a half at their displayed decimals: 3
values that R's round shows as another number than half away from zero: 2
  of them the example formats: 2; its text is ours for 2, R's for 0
```

The two are a third quartile of height (172.85: "172.9" by the registry and
in the example, "172.8" by R) and a third quartile of a change from baseline
(0.25: "0.3" against "0.2"). Four more texts differ only because `format`
writes one small value with an exponent; tfrmt formats a column of values at
once, so they are not counted.

### What the example's formatted values show about a pattern

All 3,734 formatted values of the example, by the pattern of their
operation and by their shape (9 stands for any digit):

| Pattern | Shapes, with the number of results |
| --- | --- |
| `(N=XX)` | `(N=99)` 3 |
| `XXX` | `9` 775, `99` 53 |
| `( XX.X)` | `(  9.9)` 767, `( 99.9)` 61 |
| `XX.X` | `99.9` 414, ` 9.9` 225, `- 9.9` 199, `999.9` 144, `-99.9` 50 |
| `(XX.XX)` | `(99.99)` 142, `( 9.99)` 116 |
| `X.XXXX` | `9.9999` 10, `9` 1 |
| `XX` | `99` 320, `999` 233, `-99` 90, `99.99` 62, `-9.99` 27, `9.99` 27, `999.9` 6, `99.9` 3, `9` 3, `-9` 3 |

A mask with a decimal point is padded with blanks to its length, the minus
sign stands before the padding, a longer number is not cut, and a mask
without a decimal point is not padded. The example shows a longer number
under `XX.X` and under `XX`; under `( XX.X)` none of its values is longer
than the mask, so that "( 100.0)" is not cut is the registry's choice, not
something the example shows. Two things do not follow their
pattern: 125 minima and maxima are shown with the decimals of the data
under `XX`, and one p-value of 1 is shown as "1" under `X.XXXX`. Neither is
in the output of real-3a; the rest of real-3 meets them (see "Left for the
rest of real-3").

### The example's table shell

The output `Out14-3-1-1` names one reference document,
`AE_Summary_Table_Shell.pdf`. The file is in the pinned ARS repository
(commit `2c9b4b6`), in the folder of the example,
`workfiles/examples/ARS v1/`, where the `location` of the document points.
Its SHA-256 is
`7c744c2d93c981244aa1414fdff9575d6eea34329a40b5a180de44f473e80a63`.

The first version of this ADR said the file was not in the repository.
That was wrong, and nothing recorded how it had been looked for. The
review found the file (finding F1); the author then listed the folder and
read the shell as text (poppler 24.02; the text is not committed). It
shows:

- three columns under the names of the three arms, each with the mask
  `(N=XX)`, and the header of the row labels on the line of the masks;
- eight rows with the eight labels of the grid, in the order of the grid,
  every cell with the mask `XX ( XX.X)`: the count, one blank, the percent
  in brackets;
- above the eight rows one line without cells, "Number of subjects with at
  least one event", with the eight rows indented under it;
- the three titles and the two footnotes, and lines of a page header and a
  page footer.

Held against it, the grid of real-3a:

- The cell of the layout is the cell of the shell: count, blank, percent.
- The grid has no line above the eight rows. The same text is in the ARS
  file, as the name of the item of the list of contents above the eight
  analyses; the builder walks that list and does not take the name.
- The mask of the count is `XX` in the shell and `XXX` in the
  `resultPattern` of the operation, which the mock shell follows.
- The first title is "Table 14.3.1.1" in the shell and
  "Table 14.3.1.<x>.<y>" in the ARS file, which the grid follows; the note
  on the abbreviation ends with a point in the ARS file and without one in
  the shell.
- The page header and footer are not in the grid; grid schema version 0
  has no place for them.

Four more shells are in the same folder, by their names those of the other
four outputs. They were not read.

## Decisions

1. Layout spec v0 is our own format. tfrmt's JSON is not the on-disk layout.

   - A grid cell must name the ARD rows behind it (section 7.4; P3 of
     section 4.6). tfrmt gives texts and no such link. It would have to be
     built again next to tfrmt, from the same mapping the layout holds.
   - A number is rounded once, by a rule the registry declares (sections
     7.2 and 7.3), and the rule is a decision of the catalog
     (`tfl.rounding.rule`). tfrmt rounds with R's `round` and has no option.
     On the pilot that changes 2 of the 3 results that lie on a half, and
     the example agrees with the registry on both (T1).
   - Its JSON is R code in text. Reading it means running R with tfrmt and
     gt. The compiler that writes layouts, the grid builder and the scorer
     are Python; the R library is shared by all checkouts, and a package
     outside the lock fails `specfirst doctor` in every track.
   - Its input is not an ARS result set. The mapping from an analysis, an
     operation and a group to a row, a column and a part of a cell is
     needed either way. That mapping is what a layout is; tfrmt starts
     after it.
   - A format without a schema and without a version is whatever the
     installed version writes.

   What is taken over from tfrmt is the idea, not the format: a cell is a
   template with named parts, a shell shows the masks of its patterns, and
   the count of a column belongs to its header. A projection of a layout
   and an ARD into a tfrmt object, for someone who renders with gt, stays
   possible: renderers are swappable (section 7.1). It is not built.

2. The format (`specfirst.machine.layout`, which documents every key). A
   layout is one YAML or JSON file per ARS output:

   ```yaml
   layout: 0
   output: Out14-3-1-1
   columns:
     grouping: AnlsGrouping_01_Trt
   rows:
     - kind: header
       cell: "{N}"
       parts:
         N: {analysis: An01_05_SAF_Summ_ByTrt, operation: Mth01_CatVar_Count_ByGrp_1_n}
     - kind: analyses
       cell: "{n} {pct}"
       parts:
         n: {operation: Mth01_CatVar_Summ_ByGrp_1_n}
         pct: {operation: Mth01_CatVar_Summ_ByGrp_2_pct}
       analyses: [An07_01_TEAE_Summ_ByTrt, An07_02_RelTEAE_Summ_ByTrt]
   ```

   - It holds rules and names, no numbers (rule R6).
   - The column axis is one ARS grouping: one column per group, in the order
     of the grouping. For a data-driven grouping the layout may list the
     values, which fixes their order and lets a shell be built without
     data.
   - The row axis is a list of blocks. Version 0 has two kinds: `header`,
     one row that is shown in the table header, and `analyses`, one row per
     listed analysis. In both, an analysis has the column grouping as its
     only grouping.
   - A cell is a template with one `{name}` per part; a part is one result,
     shown by a pattern.
   - What the ARS file holds is taken from it and may be overridden: titles
     and footnotes (the Title, Abbreviation and Footnote sections of the
     display), the header of the row labels, the label of an analysis, the
     name of a group, the `resultPattern` of an operation. A file compiled
     by std-1 has no result pattern (ADR-004, decision 5): its layout names
     the pattern of every part.
   - The layout is checked by code, not by a schema in `standard/schemas/`.
     A schema there needs an ADR the owner approves; it should wait until
     the format has met the other three table families.

3. A pattern is a registry entry: `display.pattern`, with seven numbered
   statements and 18 vectors. Statements 3 to 5 (padding, no padding without
   a decimal point, the place of the minus sign) are what the table above
   shows; they are the rule of the example, taken as version 0 of ours. It
   rounds by `display.round.half_away_from_zero`. The rounding rule is not
   yet an option of the entry: the registry has one rule, and the catalog's
   second alternative (`half_even`) needs an entry before a layout can ask
   for it.

4. A count under a column header is a cell. Version 0 of the grid schema
   gives a column an ID, a label and a spanner. "(N=86)" is a printed number
   and must reach its ARD row (P3), so it is a cell of a row whose section
   is `@header`; a renderer shows such rows in the table header, and the
   label of the row is the header of the row labels. No body section may
   have that name. The example of the schema file writes the count into the
   column label ("Placebo (N=86)"); a layout can still do that with
   `columns.labels`, but then the number has no trace, and the builder does
   not do it.

5. P2 for grid text (`specfirst.machine.grid.compare_reference`). The
   expected text of a cell is its template filled with the reference's
   `formattedValue` of every result it shows.

   - A cell that differs is classified when every part that differs shows
     a result whose own difference has a class and a proof that holds, the
     reference's formatted value is its own raw value under the same
     pattern, and all such parts have one class. The class of the cell is
     that of the result. So the exceptions file needs no second entry for a
     result that is wrong in the reference and therefore wrong in its cell.
   - Any other difference is a difference of display. It has no class and
     blocks the gate. A proof kind for it is added to the exceptions file
     when the first real case needs one, with a planted defect, as
     `results.py` does for results.
   - The check also holds the grid against the layout and the ARD (a grid
     file that was changed does not pass as built), asks that every result
     the reference formats for an analysis of the output is shown by a
     cell, and that the rows show the analyses in the order in which the
     reference lists them.
   - What it does not see: the ARS file formats results, not cells, and
     the expected text of a cell is built with the layout's own template.
     So which results share a cell, in which order, and with what text
     between them is held against nothing in real-3a; the same holds for a
     part of a body row that names another analysis than that of its row
     (review, finding F3). The example's table shell does show the cells
     (see "The example's table shell"). A check of the mock shell against
     it is left for the rest of real-3.

6. The trace of a cell (`specfirst.machine.graph.add_displays`): `shows`
   from a cell to each ARD row in it, recorded by the builder; `computes`
   from an ARD row to its analysis, and to the analysis of its denominator
   when it is a percent; `reads` from an analysis to every ADaM column the
   ARS file names for it, in any role. An edge of schema version 0 cannot
   carry the role (variable, set, subset, grouping, key); `coverage.json`
   has it per analysis. Only what a built grid shows gets a node. A node of
   an analysis is `ars:<analysis ID>`.

7. The kit. `kit.yaml` lists, per reporting event, the outputs that are
   built as grids, each with its layout: a file of our own in
   `kits/<kit>/gold/layout/`, copied into the build like the exceptions
   file. The list is the limit of the display checks (ADR-005: a part is
   limited by a list). A build writes `gold/grid/<output>.json`, the mock
   shell `gold/grid/<output>.shell.json`, and a page for each in
   `gold/out/`. Section 8 puts layout files under `gold/spec/`; in a kit of
   real data only the manifest may fill that folder, from the fetch cache,
   so our own layout is kept apart from it.

## For std-2: from layout draft 0 to version 0

The four house templates are not changed here (they are the std track's).
What version 0 asks of them:

| Draft 0 | Version 0 |
| --- | --- |
| `output: {id, title}` | `output: <id>`; the title is taken from the ARS display, or written as `titles` |
| `columns.grouping`, `columns.order` | `columns.grouping`; for a data-driven grouping `columns.values` in the order the rule gives (ascending dose, protocol order: the builder needs the arms of the design for it, ADR-004) |
| `columns.header_count: <analysis>` | a `header` block whose part names that analysis and its count operation |
| `columns.total`, `columns.comparison` | not in version 0: columns of another grouping or of a test come with the rest of real-3 |
| `rows[]: {label, kind: count_percent, analysis, total_analysis}` | an `analyses` block with the cell `"{n} {pct}"` and one listed analysis per row |
| `rows[]` of kind `continuous`, `categorical` | not in version 0: one row per statistic, one row per group of a row grouping |
| `formats: {rounding, percent, decimals}` | a `pattern` per part ("XX.X"), which carries the decimals and the form of a percent; the rounding rule when the registry has a second one |

The compiler records what a decision binds in a layout as
`layout:<unit>/<part>` (ADR-004, point 4 for the owner). Version 0 keeps
that form; the parts are `columns` and `rows`.

## Left for the rest of real-3

- The example's table shells: pin them in `kit.yaml`, and hold the mock
  shell of a build against the text of its shell (the row labels in order,
  the mask of every cell, the masks under the column labels). The planted
  layouts that pass today (the percent before the count, another text
  between the parts, another header) must fail then. Give the line above
  the eight rows of the adverse event summary a place in the layout, or
  record it as a difference, and settle the mask of the count.
- The kinds of block the other four outputs need: rows per group of a row
  grouping (defined groups for demographics, data-driven and nested for
  organ class and term), a row per statistic, columns that compare two
  groups, a total column; sort and threshold rules.
- Display rules that are not entries yet: p-value formats and the
  truncation of long terms (E25).
- The two places where the example does not follow its own pattern (125
  minima and maxima under `XX`, one p-value shown as "1"): each needs a
  class and a proof kind for a difference of display, or a rule.
- Four medians of the vital signs where our value is a half only up to
  floating error (0.05 computed as 0.04999...): the example shows " 0.1",
  the display rule gives " 0.0" for the value as computed. The registry has
  to say how a value this close to a half is rounded. Over all 3,734
  formatted values of the example the display rule gives the example's text
  for 3,580; 24 differ with a result that is classified, and these 130
  differ by display only. None of them is in the output of real-3a.
- The viewer and the citations through the ARS `documentRefs`.

## Consequences

- gen-2a and read-1a build and score the adverse event summary with this
  builder. A compiled study has a data-driven treatment grouping and no
  result pattern: its layout lists `columns.values` and a pattern per part.
  One limit of version 0 was found by the review (finding F2): with a
  data-driven column grouping, an arm that has no record of an analysis has
  no group there (rule I9) and no ARD row, and the builder stops. With
  defined groups the same data give "0 (  0.0)". What such a cell shows
  must be decided before a compiled study with an empty row is built.
- A layout is small and readable, and a reviewer can read a shell before
  data exist. It is one more format of our own to maintain; the price was
  judged against a dependency that cannot give the trace.
- If the owner prefers tfrmt as the layout, the change is in
  `specfirst.machine.layout` and `grid.plan`: the plan of a grid (which
  result in which cell, under which pattern) is the interface, and the
  checks, the trace and the renderer read the plan and the grid, not the
  layout file.
