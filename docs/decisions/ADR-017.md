# ADR-017: A kept run of the reader, bound by bytes where the slice reaches and by version where it does not

Status: approved by the owner for the slice of ADR-005 only, 2026-11-19
(the section "The owner's answer"), and carried out by the part adr-017 of
the read track (docs/reports/adr-017.md). Proposed by the read track the
same day, before real-5b changes the method registry. It changes ADR-010,
decision 9 (how the gate read-2a reads its text for arm R, which the owner
approved for the slice of ADR-005 only) and adds the check that finding K4
of the real-5a review asks for. PLAN.md, `standard/schemas/`, `catalog@1`
and the house standard `open-default@1` are not changed.

## Context

ADR-010, decision 9: a gate never calls a model, so the dry run of arm R is
made once and kept in `src/specfirst/harness/kept/<run>/`. The gate writes
kit 4 of the gate seed again, builds the task of the kept run again and
asks that "its manifest must be the recorded one, so the run read exactly
this task", and `runs.check` asks that the SHA-256 of the kit's
`kit.yaml` be the recorded one.

The kept run is now `R-task-04119188ff71` (real-5a, USD 0.58 computed from
the tokens). It is tied, byte for byte, to:

- the task's manifest, 92 files: TASK.md; `inputs/docs/` (2);
  `inputs/data/sdtm/` (23); `inputs/house/` (15); `knowledge/` (the core
  skill and the reading notes of the four units, 5); `standard/catalog/`
  (catalog.yaml and 43 entries); `standard/methods/registry.json`;
  `standard/schemas/decision-record.schema.json`;
- the kit's `kit.yaml`, which holds the generator's version, the catalog's
  name and version, the house's label, the SHA-256 of the seed and of every
  file of the kit (`files`: data, documents, gold, twin), and `pins`: the
  versions of the engines (yamaa, pyarrow, R) and `registry_sha256`.

real-5a added three entries of kind `model` to the method registry. The
slice uses none of them. Still `registry.json` in the task and
`registry_sha256` in `kit.yaml` changed, the check "arm R, kept dry run"
failed, and the owner paid for the dry run again (lesson 68). real-5b adds
more entries (the mixed model, CMH). A new lock of pyarrow, yamaa or R
changes `pins.engines` and fails the check the same way.

The owner's direction (2026-11-19, relayed by the base session in real-5a;
docs/state/read.md, Open): tie a kept run to versions instead (the
registry's, `catalog@N`, the generator's), so that it no longer goes stale
on every change. The review of real-5a adds:

- K5: a kept run is tied to more than those three, and a binding by version
  weakens decision 9's "exactly this task". Its recommendation (the owner's
  choices, item 1): an ADR of the read track that says what is bound by
  version and what still by bytes, approved before real-5b.
- K4: the check holds the kept output files for validity and for the scan,
  not against what the run wrote. A kept `decisions.jsonl` with one record
  left out, or with `tfl.percent.format` changed to another valid value,
  passes.
- K3: the kept transcripts hold the CLI's `rate_limit_event`. The owner
  keeps it as it is (2026-11-19); this ADR does not touch it.

What has a version today:

- the catalog: `catalog@1`, frozen (issue #28 proposes rules for steps of
  version; none is decided);
- the house standard: `open-default@1`;
- the generator: `GENERATOR` (`gen-3a.2`), in every `kit.yaml`.

The method registry has no version number. A look at kit 4 of the gate
seed on `main` `1ef7636`: its gold reporting event binds 2 of the
registry's 12 entries (`ars.bind`: `count.subjects`, `percent.subjects`),
and its cells are shown through `display.pattern` with the rounding rule
the layout names (`specfirst.gen.display`).
The three entries of kind `model` and the tests are not reached.

## Decisions

1. **The principle.** A kept run stays bound by bytes to everything the
   reader of the slice reads and everything the check scores or scans
   against. It is bound by version only to the parts of shared files that
   the slice does not reach. For arm R the gate then reads "a dry run of
   each arm ends within budget" as: the kept run read a task that agrees
   with the task built now on every bound part (decisions 2 and 3), and it
   ended within budget, with valid files that are the run's own (decision
   5) and a clean scan. Today's reading is "exactly this task". That is
   the owner's to accept (lesson 47), for the slice of ADR-005 only, like
   ADR-010, decision 9.

2. **Still bound by bytes.**

   | Part | Files | Why bytes |
   | --- | --- | --- |
   | TASK.md | 1 | the task builder's text; the reader reads it first |
   | the skills | `knowledge/`, 5 | the condition under test |
   | the documents and data | `inputs/docs/`, `inputs/data/` | what the reader reads the decisions from |
   | the house standard | `inputs/house/`, 15 | read for the defaults; named `open-default@1` as well |
   | the catalog | `standard/catalog/`, 44 | read for the questions and alternatives, and every entry also to decide what is unmapped; named `catalog@1` as well |
   | the record schema | 1 | the form of every record |
   | the kit | every file `kit.yaml` lists under `files` | the scan's canaries (gold, twin) and the score's gold come from them |

   The catalog and the house are named by version too (decision 3), and
   they are compared by bytes as well. `catalog@1` is frozen, so within the
   version the two say the same. A step of version, under rules the std
   track may set (issue #28), is another catalog and makes the run stale.
   Because the kit's files are bound by bytes, the scan of the kept run
   against the canaries of the kit written now is a scan against the gold
   the reader could have reached.

3. **Bound by version.**

   - **The method registry, by the entries the slice reaches.** These are
     the entries the machine looks up when it builds the kit's gold: those
     `ars.bind` gives the methods of the kit's reporting event, and those
     the build of the cells calls (`display.pattern` and the rounding rule
     the layout names). The kept run records
     each with the SHA-256 of the entry in canonical JSON. A change of one
     of them makes the run stale, and so does a slice that reaches one
     entry more or less than the record. An entry added, or an entry the
     slice does not reach changed, does not. The registry has no version
     number; this set is its version for the run. It is computed, so no one
     has to remember to step a number (rule R1).
   - **The generator, by its version**: `generator` of `kit.yaml`, compared
     as part of `kit.yaml` without `pins` (below).
   - **The catalog and the house, by name and version** as `kit.yaml`
     gives them (`catalog: {name, version}`, `house`), and by bytes
     (decision 2).
   - **The engines are not compared.** `pins.engines` (yamaa, pyarrow, R)
     changes with a lock. If a new engine changes any file of the kit,
     `files` shows it.
   - **`kit.yaml` without `pins`.** The SHA-256 of `kit.yaml` read as data,
     with `pins` taken out, in canonical JSON. `pins.registry_sha256` is
     replaced by the entries the slice reaches.

4. **The binding file.** `runs.keep` writes `binding.json` beside the
   record. It holds the SHA-256 of the task's manifest without
   `registry.json`; the entries of the registry the slice reaches, each with
   its SHA-256; the SHA-256 of `kit.yaml` without `pins`; the generator,
   the catalog and the house as `kit.yaml` names them; and the SHA-256 of
   every file `keep` writes (decision 5). `runs.check` builds the task
   again and compares:
   - every file of the manifest but `registry.json` by bytes;
   - the entries the slice reaches now, by name and SHA-256;
   - `kit.yaml` without `pins`.

   It names the bound part that differs. When only the registry changed,
   the task has another ID; the check's line says so ("task
   task-04119188ff71, built again now: task-<other>, the same on every bound
   part"). A kept run without `binding.json` fails.

5. **The kept outputs tied to the run (K4).** The check holds every kept
   file against the SHA-256 that `binding.json` records for it. It also
   writes `out/` again from the transcript: the Write and Edit tool uses
   the CLI carried out, those without an error result. It compares those
   files with the record's `outputs` (the SHA-256 of the files as the
   reader wrote them) and, in the canonical JSON that `keep` writes, with
   the kept files. A record, a transcript and outputs edited by hand all
   together would still pass. The history of the kept folder in git shows
   such an edit, and the review of the part that keeps a run reads it.

6. **The kept run of real-5a gets its binding file without a model run.**
   For `R-task-04119188ff71` a command writes `binding.json` once. It works
   from the registry and from kit 4 of the gate seed as they are on `main`,
   and refuses unless:
   - the registry it reads has the SHA-256 the task manifest records for
     `registry.json`;
   - the kit's `kit.yaml` has the SHA-256 the record holds;
   - `out/` written again from the transcript (decision 5) matches the kept
     files.

   The first two hold on `main` `1ef7636`: the gate read-2a passed on
   clean clones of `0a58979`, the same tree for these files. The command
   is easiest before the registry changes again. After a change it can
   read the registry of an older commit, held by the same SHA-256.

7. **The gate read-2a and its plants (rule R5).**
   - Plants that must fail:
     - an entry the slice reaches, changed;
     - a file of the kit changed;
     - a kept run without `binding.json`;
     - a binding file whose entries lack one the slice reaches;
     - the two cases of K4: a kept `decisions.jsonl` with one record left
       out, and one with `tfl.percent.format` changed to another valid
       value.
   - Plants that must pass, as the clean transcript does today:
     - an entry of kind `model` added to the registry;
     - the versions of the engines changed in `kit.yaml`.
   - The plant "a kept run whose task differs by one file" stays (a skill
     changed).

8. **Scope.** For the slice of ADR-005 and the gate read-2a, as ADR-010,
   decision 9. The isolation probe kept beside the run
   (`probe-task-50024a8d7ca2`, of the old task) is no gate's evidence and
   is not touched. A new probe is not part of this ADR (review of real-5a,
   the owner's choices, item 4).

## What still makes a kept run stale, and what no longer does

Still: a change of TASK.md or of the task builder; of a skill; of a
document, the data or a gold or twin file of the kit; of a catalog or house
file, or a step of their version; of the record schema; of the generator's
version; of an entry of the registry the slice reaches; and a slice that
reaches another entry. Each needs the dry run of arm R made again (about
USD 0.6 on the owner's subscription).

No longer: an entry of the registry the slice does not reach, added or
changed (the three entries of real-5a; the mixed model and CMH of real-5b,
if real-5b changes no entry the slice reaches), and the versions of the
engines.

## Alternatives

- **A version number in `registry.json`, stepped by hand.** A step can be
  forgotten, and a step for an entry the slice does not reach still stales
  the run. Not taken (rule R1).
- **The task holds only the entries of the registry the slice reaches.**
  The task then stays the same file for file when the registry grows, and
  "exactly this task" keeps holding. It changes the task, so the dry run is
  made again once (about USD 0.6), and the reader no longer sees every
  method the standard knows (ADR-010, decision 2). It also leaves K4 open.
  It can be added to decisions 4 and 5 later. Not taken now; the owner may
  prefer it.
- **The catalog by version only.** Weaker than bytes, and it gains nothing
  while `catalog@1` is frozen. Not taken.
- **No change: one dry run per change of the registry.** About USD 0.6
  each time (real-5a paid one), and the same again on a new lock of an
  engine.

## Consequences

- real-5b's merge waits for the part that carries this ADR out to be on
  `main`, not only for this ADR. Until then the check is today's, and a
  change of the registry fails it.
- That part is the read track's: `runs.keep` and `runs.check`, the plants
  of the gate read-2a, the command of decision 6, unit tests, the gates
  read-2a and read-1a on clean clones, a review. It uses no model.
- ADR-010, "Consequences" ("a change of the skills, the task builder, the
  catalog or the generator gives another task, and the gate fails") stays
  true for those, and no longer holds for entries of the registry the slice
  does not reach or for the engines' versions.
- CLAUDE.md's note on `registry_sha256` and the kept dry runs, and lesson
  68, are amended by that part: a change of the registry fails the check
  only when it changes an entry the slice reaches.

## For the owner

1. **Approve decisions 1 to 8, for the slice only** (recommended). The
   gate read-2a then reads "a dry run of arm R ends within budget" as a
   kept run whose task agrees with the task built now on every bound part
   (decision 2 by bytes, decision 3 by version), in place of "exactly this
   task". No model run is needed now (decision 6).
2. Or the alternative "the task holds only the entries the slice reaches":
   the task identity stays exact, one dry run of arm R now (about USD 0.6).
3. Or no change: one dry run per change of the registry or of an engine's
   version.
