# ADR-010: The harness of read-2a, and how the reader reaches a model

Status: proposed in read-2a, 2026-11-18, by the executor, where PLAN.md and
ADR-005 are silent. PLAN.md, `standard/schemas/` and the catalog
`catalog@1` are not changed. Three points are the owner's and are listed
at the end: logging in the Claude Code CLI (an act only the owner can do),
how the gate reads its own text for arm R (decision 9), and the routes the
owner may prefer to the CLI. The other decisions stand unless the owner
objects.

## Context

read-2a is the part of read-2 for the slice of ADR-005: the task builder,
the adapter, isolation, the canary scan, run records with cost; the
`core-reader` skill and reading notes v0 for the four units of the slice,
taken from the catalog; the three arms S, R and C of ADR-005, decision 3.
Its gate (ADR-005, decision 1): "A dry run of each arm on one train kit
ends within budget with valid output files. The canary scan is clean."

Section 11.1 names the default adapter: Claude Code run non-interactively,
`claude -p` with `--output-format json`, the model set to Opus 5.5 and the
tools limited with `--allowedTools`, on the owner's subscription; "confirm
the flags against the current CLI reference in read-2". Section 11.2: gold,
twins and seeds are never inside a task folder; in M1 a task runs in a
temporary directory outside the repository with deny rules for the kit
store, and every transcript and workspace is scanned for canary strings
planted in gold files. Section 11.3: the reader asks with `specfirst ask`,
and the oracle answers only decisions without a house default that the
documents do not state.

What this machine has (2026-11-18): the Claude Code CLI 2.0.29, installed
with npm on Windows. The Linux of WSL, where the Python environment of the
repository lives, has no node and no CLI. A print-mode call answers
"Invalid API key - Please run /login" with 0 tokens and exit status 0: the
CLI is not logged in (gen-3a found the same; ADR-009, decision 1).

## Decisions

1. **The reader reaches the model through `claude -p`**, the route of
   section 11.1, on the owner's subscription, once the owner has logged the
   CLI in. The harness runs in WSL and starts the Windows CLI through WSL
   interop (`SPECFIRST_READER` names the program, default `claude`); the
   task folder therefore lies on a Windows drive, outside every checkout
   (`SPECFIRST_TASKS`). The flags, checked against `claude --help` of
   2.0.29 and against print-mode calls that the missing login made free:

   | Flag | Why |
   | --- | --- |
   | `-p "<prompt>"` | non-interactive; the prompt says: read TASK.md and do the task |
   | `--output-format stream-json --verbose` | every message, tool call and tool result, one JSON object per line; the last line is the object `--output-format json` gives. The canary scan needs the whole transcript, so `stream-json` replaces the `json` of section 11.1 |
   | `--model claude-opus-5-5` | Opus 5.5 by its full ID: the alias `opus` of an older CLI may name an older model |
   | `--max-turns N` | the turn budget (decision 8); accepted by 2.0.29 though `--help` does not list it |
   | `--allowedTools`, `--disallowedTools` | decision 3 |
   | `--permission-mode default` | a tool use that no rule allows is denied: print mode has no one to ask |
   | `--settings FILE` | the deny rules of decision 4 |
   | `--setting-sources ""` | no user, project or local settings can widen the rules |
   | `--strict-mcp-config` | no MCP server (the init event lists `mcp_servers: []`) |

   2.0.29 has neither `--bare` nor `--max-budget-usd`, which section 11.1
   names for the API-key route: the adapter enforces the budget itself
   (decision 8). A call that fails reports `is_error: true` with exit
   status 0, so the adapter reads `is_error` and the `result` event, never
   the exit status alone.

   Routes not chosen, for the owner (last section): an API key (a
   credential and a paid service; and this CLI lacks the flags that go with
   it), and a subagent of an executor's session as the reader. The second
   does not meet section 11.2: a subagent has the permissions of the
   session that starts it and can read gold, the store of model text and
   that session's own transcript, and no script can call it. It is not
   used without the owner's approval.

2. **The task folder** (section 11.1; ADR-005, decision 2). Written by
   `specfirst.harness.task.build` from a kit, the catalog and the skills:

   ```text
   <task>/
     TASK.md                      what to do, the files, the formats, the tools
     inputs/docs/                 protocol.md, sap.md: the natural form (IDs protocol, sap)
     inputs/house/                the house standard, as the kit has it (ID house)
     inputs/data/sdtm/            stage C: the visible SDTM, Parquet and Dataset-JSON, Define-XML
     inputs/data/adam/            stage T only: the ADaM of gold on the visible data
     standard/catalog/            catalog.yaml and entries/ (the questions and alternatives)
     standard/methods/registry.json
     standard/schemas/decision-record.schema.json
     knowledge/core-reader/SKILL.md       always
     knowledge/<unit>/SKILL.md            the reading notes, condition `notes` only
     bin/ask, bin/check           the two tools (decision 3)
     out/                         empty: decisions.jsonl, questions.jsonl, unmapped.jsonl
   ```

   Not in it: `kit.yaml`, `study.json`, `gold/`, `twin/`, the seeds, the
   store `src/specfirst/gen/rewrites/`, and of the catalog its `knowledge/`
   (the notes are the condition under test), `phrasings/`, `templates/`
   and `probes.yaml`. The folder is a pure function of the kit, the stage,
   the condition, the catalog and the skills (rule R4); its ID is a prefix
   of the SHA-256 of its manifest and names no kit, seed or split. The two
   wrappers in `bin/` name the run's private folder and are not part of the
   manifest. The prompt names the knowledge files that are present, so the
   two conditions of section 11.1 (`catalog`: the core skill only;
   `notes`: with the units' reading notes) differ only in the files.

3. **The reader's tools.** Read, Glob, Grep, Write and Edit, in the task
   folder; Bash for `bin/ask` and `bin/check` only. Not allowed: Task
   (subagents), WebFetch, WebSearch, NotebookEdit, Skill, SlashCommand,
   BashOutput, KillShell.

   - `bin/ask "<question>" --decision <id> [--unit <unit>]` runs
     `specfirst ask` (section 11.3). It answers from the run's copy of the
     kit's `gold/oracle.yaml`, and only a decision that the file lists; any
     other decision gets "no answer". Every ask is written by the harness to
     the run's `asks.jsonl` and to the task's `out/questions.jsonl`. The
     scorer takes what was asked from `asks.jsonl` (`scorer.run(asked=...)`;
     gen-3a review, finding D8).
   - `bin/check` runs the validation of decision 6 on the task's `out/`,
     so a reader can repair its files. It reads the task folder and the
     catalog, nothing else.
   - `specfirst preview` of section 11.1 (building one's own decisions on
     the visible data) is not given in the slice.

4. **Isolation in M1** (section 11.2). The task folder is outside every
   checkout and is the reader's working directory, with no `--add-dir`.
   A file tool that reaches outside the working directory needs a
   permission that print mode cannot give. On top of that the settings file
   denies Read, Edit, Write, Glob and Grep on: the folder that holds every
   checkout (`D:/trial_work`, with the employer's `reference/` in it), the
   kit store, the run store, the store of model text, the folder of the
   seed file, the user's `.claude` (the transcripts of other sessions hold
   gold), `Desktop`, `Documents` and `Downloads` (a person's own files, rule
   2 of section 2.1), any folder `SPECFIRST_DENY` names, and the WSL file
   system (`//wsl.localhost`, `//wsl$`). Bash runs the two wrappers and
   nothing else; a wrapper puts the run and the task after the reader's own
   arguments, so a reader cannot point it at another folder. A short
   isolation probe (decision 8) asks the model to read a protected file of
   each kind (the kit on the WSL share, the store on drive D, the run's own
   oracle on drive C, by Read and by Bash) and must find every attempt
   denied. It never names a file of a person's own folders.

   The limit, to be stated in every M1 report: the reader runs as the
   owner's Windows user under these rules, not in a container where gold
   is not mounted (that is M2). A rule the CLI does not apply, or a path no
   rule names, leaves gold readable, and the canary scan sees a read only
   when its text reaches the transcript or the workspace.

5. **The canary scan.** Protected: of the kit, every file outside
   `inputs/` (`kit.yaml`, `study.json`, `gold/`, `twin/`, with
   `gold/oracle.yaml`); the store of model text; the seed of the kit; and
   the private files of the run. Two kinds of canary:

   - planted: every private file the harness writes outside the task
     folder (the copy of the oracle, the settings, the pointer to the
     kit) carries a canary string derived from the SHA-256 of the kit's
     manifest and the file's name;
   - drawn from gold: a kit is written by the generator, its manifest
     holds the SHA-256 of every file, and kits are generated again, never
     patched (docs/state/gen.md); the harness cannot plant a string in gold
     without making another kit. So every line of a protected text file,
     with blanks collapsed, of at least 24 characters, is a canary (a line
     longer than 120 characters gives its pieces of 80), unless it stands
     somewhere in the task folder, in an answer the oracle gives, or in a
     gold decision record as a reader writes it (its value, statement and
     citations as JSON), or unless all but 16 of its characters stand inside
     a statement of the gold decisions or an answer of the oracle (a reader
     writes those with a few words of its own around them): that is what a
     reader is meant to read or to write. The seed is a canary whatever its
     length.

   Scanned: every string of every event of the transcript, decoded from
   its JSON, and every text file of the workspace after the run. Clean
   means no canary is found; a hit names its file and its line. Parquet
   files are not drawn from: every SDTM table of a kit has a Dataset-JSON
   copy, which is; the ADaM Parquet of gold has none (a limit). That the
   generator plant canary lines in gold and twin files is booked for the
   gen track.

6. **Valid output files.** `out/decisions.jsonl`: every line a JSON object
   that fits decision-record schema v0; an entry of the catalog in a unit
   the task scores; a value the standard form accepts for that entry and
   unit (`StandardForm.check_value`); no `binds` and no `identifiable`
   (filled by the compiler and the machine, section 4.3); every citation
   names a document of the task (`protocol`, `sap`, `house`) and an anchor
   that stands in it; one record per decision. `out/questions.jsonl`: every
   line names a catalog entry (`decision`) and a question; it is the ask
   log of the run, line for line. `out/unmapped.jsonl`: every line names a
   document of the task and an anchor that stands in it. All three files
   exist (they may be empty) and are UTF-8 JSON lines.

7. **The run record and its cost** (section 9.2, cost). `run.json` of a run
   names the run, the arm, the stage, the condition, the task (its ID and
   the SHA-256 of its manifest), the kit (ID, split, generator, SHA-256 of
   `kit.yaml`), the reader (adapter, CLI version, the model asked for and
   the models used), the budget and the cost: tokens by kind and by model
   (input, output, cache write, cache read), turns, wall time measured by
   the harness, API time, and US dollars computed from the tokens with the
   prices below, beside the CLI's own `total_cost_usd`. On the owner's
   subscription no money is charged per token; the dollar figure is what
   the run would cost on the API. Prices per million tokens, Claude API,
   as the claude-api reference of 2026-11-03 gives them:

   | Model | Input | Output | Cache write 5 min | Cache write 1 h | Cache read |
   | --- | --- | --- | --- | --- | --- |
   | claude-opus-5-5 | 4.00 | 20.00 | 5.00 | 8.00 | 0.20 |
   | claude-sonnet-5-5 | 2.00 | 10.00 | 2.50 | 4.00 | 0.10 |
   | claude-haiku-5-5 | 0.10 | 0.50 | 0.125 | 0.20 | 0.01 |
   | claude-haiku-4-5 | 1.00 | 5.00 | 1.25 | 2.00 | 0.10 |

   Cache writes are 1.25 times (5 minutes) and 2 times (1 hour) the input
   price, cache reads a tenth of it, as the reference gives them. A model
   ID with a date suffix takes the price of the ID it starts with (the CLI
   may use a small model for its own background calls). A model without a
   price fails the record. Arms S and C use no model:
   their tokens and dollars are zero. A record is a log of a run and may
   hold its wall time (rule R4 allows clocks in logs); the files the
   scorer reads do not.

8. **The budget of a dry run.** Arm R: at most 100 turns (`--max-turns`),
   45 minutes of wall time (the adapter stops the process after that), and
   USD 10 computed. Arms S and C: 10 minutes each. A dry run is within
   budget when every figure of its record is at or below its limit and the
   reader ended by itself (a `result` event, `is_error` false). The dry
   runs: kit 4 of the seed of the gate gen-2a (`gen-2a/kit-4`: train, the
   ask demo, two decisions for the oracle), stage C, condition `notes`.
   The isolation probe: one short run, at most 10 turns and USD 1. Model
   use expected for the part: one dry run and one probe, about USD 3 to 6.

9. **The gate `read-2a`, and how it reads its text for arm R.** A gate
   never calls a model (rule R4; a clean clone and CI have no logged-in
   CLI). The dry run of arm R is made once, with the model, by `specfirst
   task run --arm R`, and kept in `src/specfirst/harness/runs/<run>/`: the
   record, the transcript (JSON lines, written in ASCII), the output
   files, the ask log and the manifest of the task. The gate then

   - writes kit 4 of the gate seed again (a process of its own) and holds
     its gold (`kits.gold_problems`);
   - builds the task of the recorded run again: its manifest must be the
     recorded one, so the run read exactly this task;
   - holds the recorded run: within budget, valid output files, the canary
     scan of its transcript and workspace clean against the canaries of
     the kit written now; and scores it, with the questions it asked
     (report only);
   - runs arms S and C on the kit through the harness, live: the same run
     folder, record, validation and scan; their scores are reported;
   - runs the adapter live with a stub reader, a program that speaks the
     CLI's `stream-json` and writes output files: within budget, valid,
     clean;
   - plants a defect for each of its checks (rule R5): an output file
     that breaks each rule of decision 6; a record over each limit, and
     one with `is_error`; a transcript and a workspace file with a canary
     of each protected kind, and a clean transcript that holds what a
     reader may read and write; a task folder with a gold file in it;
     settings without one deny rule; a skill with a kit ID in it, and a
     skill that is not its rendering; an oracle that answers a decision it
     does not list; a recorded task that differs by one file.

   Reading "a dry run of each arm ends within budget" as "for arm R, the
   dry run is checked from its record" is how this part reads the text of
   its own gate, and that is the owner's to accept (lesson 47).

10. **The `core-reader` skill and reading notes v0** (section 10).
    `skills/core-reader/SKILL.md` is the shared procedure, written by
    hand: read, locate, quote, record, apply the silence rule, ask, list
    what is unmapped, check the files. `skills/<unit>/SKILL.md` for
    `mod-treatment`, `mod-populations`, `mod-ae-emergence` and
    `tfl-ae-summary` is rendered from the catalog: the question, the
    alternatives with their statements, the house default and the reading
    note `knowledge/<entry>.md` of every entry of the unit
    (`specfirst task skills --write`); the gate holds the files equal to
    the rendering. Both are Agent Skill folders (a `SKILL.md` with `name`
    and `description` in its front matter, the format of pharma-skills,
    E16). The leak check of section 11.4: no skill holds a kit ID, a study
    ID, a subject ID or the seed of a kit of the gate set, or a paragraph
    of the store of model text.

11. **Kits.** Every kit is written outside every checkout. The dry runs use
    kit 4 of the gate seed, a train kit. read-2a scores no dev or test
    kit, and never kits 5 to 10 of the gate seed as dev or test kits
    (their statements are in the store; gen-3a review, finding D7). Arm S
    builds nothing on the chain: `ae.related.values` has no house default
    in `catalog@1` (ADR-008, "For the owner", item 1). The run reports it
    as it is.

## Consequences

- Until the owner logs the CLI in, arms S and C and the stub reader run;
  arm R does not, and the gate `read-2a` fails at its check of the
  recorded run, because there is none.
- A recorded run belongs to the task it read. A change of the skills, the
  task builder, the catalog or the generator gives another task, and the
  gate fails until the dry run of arm R is made again.
- The harness depends on the Windows CLI through WSL interop. Another
  agent that honours the folder contract can take its place: the adapter
  is a program that writes `stream-json` and the files of `out/`.
- Model text enters the repository again: the transcript of one run of
  the reader on a train kit of a development seed (our own text, MIT,
  written in ASCII).

## For the owner

1. **Log in the Claude Code CLI on this machine.** In a Windows terminal
   (PowerShell): run `claude`, type `/login`, choose the Claude account
   with the subscription and finish in the browser; then `/exit`. The
   check: `claude -p "Reply with OK" --output-format json --model
   claude-opus-5-5` prints `"is_error":false`. The executor never handles
   the credential. Then the isolation probe and the dry run of arm R run
   (decision 8), and the gate.
2. **The reading of the gate** (decision 9): the dry run of arm R is made
   once with the model and the gate checks it from its record, while arms
   S and C and a stub reader run live. Recommendation: approve, for the
   slice. A gate that calls a model would give another answer on each run
   and cannot run on a clean clone or in CI.
3. **Other routes**, if the owner prefers not to log in: an API key
   (`ANTHROPIC_API_KEY` set by the owner; a paid service; the adapter needs
   no change), or a subagent of an executor's session as the reader, which
   does not meet section 11.2 (decision 1) and is not recommended.
