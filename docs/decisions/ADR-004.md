## Context

std-1 delivers the decision catalog for the M1 families, the standard form
with its renderer and parser, the compiler, and the house standard
`open-default@1` (PLAN.md section 13.4). Sections 4 and 5 of the plan are
contracts and give the fields; they leave the exact formats open. This ADR
records every choice std-1 made where the plan is silent, and every place
where it departs from an example or a list of the plan. It also answers the
four open schema points of ADR-000, item 7.

No version 0 schema of base-0 was changed. One schema was added.

## Decisions

1. The schema of a catalog entry (`standard/schemas/catalog-entry.schema.json`,
   version 0). It takes the fields of section 5.1 and refines them:
   - `units` in place of `unit` for a question that every table family
     answers for its own output (appendix B, "each table family"). A
     decision record then names one table family in `unit`, and the pair
     (entry, unit) identifies the decision. The statement names the output
     with the reserved slot `{output}`.
   - `house_default` is an alternative ID, null, or one ID per unit for an
     entry with `units`.
   - A slot is declared with a type (`int`, `number`, `text`, `name`, a
     list of one of these, or `records`), optional limits or choices, and
     at least two example values. The round trip and the compile check run
     on every example.
   - `definition` (per alternative) and `notes` (per entry) say what a
     statement means where the sentence alone leaves room. They are part of
     what the owner approves.
   - `sources` are objects, not strings: a key of
     `standard/catalog/sources.yaml` and the place in the source. A source
     that is pinned in `third_party/sources.yaml` also names a file and may
     name a text that must stand in it; the gate checks both on the fetch
     cache. A published document (ADaMIG, ICH E3, the FDA guide, admiral)
     cannot be checked by script: such a citation is judged, and the gate
     log counts the two kinds apart.
   - `probes` are IDs of `standard/catalog/probes.yaml`. A probe says which
     pairs of alternatives it separates and which slots it varies; the
     checker asks for every pair and every slot. A probe has one of three
     kinds: `record` (a subject or record to plant), `structural` (nothing
     to plant; the gate compiles each claimed pair and asks for different
     table files, unless the probe names in `needs` the other decision the
     difference depends on) and `design` (the design must have a property,
     such as arms listed out of dose order).
   - A slot that holds a table may state rules that keep the table from
     contradicting itself (`unique`, `ascending`, `ranges`, `field_min`).
     A window with its lower limit above its upper one is then not a
     decision: it is neither rendered nor parsed.

2. The standard form. Each slot type has one canonical text (text in double
   quotes, integers without leading zeros, a whole number never written as
   a decimal), so rendering and parsing are exact inverses. A statement is
   parsed by matching it against every template; it must fit exactly one.
   A document is Markdown with one section per unit and one anchored line
   per decision, `[<section>/s<n>] <statement>`. The anchor is what a
   citation names. The parser is strict: a line that holds an anchor and is
   not a statement at the start of the line is an error, and so is a
   document written for another catalog version.

3. Compile templates are YAML data with a few directives (`$get`, `$if`,
   `$for`, `$dict`, `$pick`, `$concat`, `$fn`), evaluated on data. The
   example of section 5.1 names a Jinja file (`.yaml.j2`). A text template
   lets a slot value change the structure of the YAML; a data template
   cannot. It also needs no new dependency.

4. ADaM. The house parent spec of a dataset holds what no decision changes
   and reads columns that decisions own. Each alternative has one yamaa
   fragment that writes those columns, often working columns whose names
   start with an underscore. The compiled spec of a dataset is one entry
   file: the parent, one included fragment per decision, the paths and the
   output columns. Two decisions never write the same column, so nothing
   has to be merged by hand; yamaa composes the layers. A default is
   compiled like a stated decision: the parent spec does not hold the
   defaults, the catalog does (`house_default`), and `STANDARD.md` states
   them. E18 reads "parent specs carry the house standard"; here they carry
   its structure and its conformance variables. The ADaM `binds` of a
   decision are the columns its fragment writes. They may be working
   columns (`adam:ADAE._TEEND`), where the example of section 4.3 shows the
   dataset variable (`adam:ADAE.TRTEMFL`): the variable is reached through
   the `derives_from` edges of the resolved spec.

5. Tables. A decision of a table family sets named parameters; the house
   has one ARS template and one layout template per family that read them.
   The ARS conventions follow the CDISC example "Common Safety Displays".
   A total column is a second grouping factor with one group. A method
   option that ARS has no place for (the quantile definition) is a
   parameter of the analysis (`programmingCode.parameters`). The compiled
   ARS file holds no result pattern: decimals, percentage and p-value
   formats are decisions, and the layout file alone holds them (section
   7.2: rounding happens once, at display). The compiler drops every
   analysis set, grouping, data subset and method that no analysis uses,
   and refuses a study whose tables read an ADaM variable that no decision
   writes, or that does not say for every table family whether its output
   is planned. The `binds` of a decision to ARS elements and layout parts
   are proven by mutation (`bind_tables`): an element is bound when another
   value of the entry changes or removes it. The other values are every
   alternative with its examples and each list of the value with one item
   left out; the edge is complete for these values only. It costs one
   compile per other value, so it runs on request, not in every compile.

6. The layout files are a draft (layout draft 0). real-3 fixes the layout
   format in ADR-003; std-2 aligns the house layout templates with it.

7. What changed against appendix B. The appendix allows std-1 to rename,
   split or drop entries. 43 entries remain (62 questions when an entry
   with `units` is counted once per table family; 96 alternatives).
   - Left out, each with its reason in `standard/catalog/catalog.yaml`:
     `ae.teae.worsening`, `ae.severity.worst`, `ae.occurrence.flags`,
     `disp.reason.source`. Two alternatives are left out as well:
     the mean of pre-dose records as baseline, and the average of the
     records in a window. Both need a derived record built by aggregation.
   - Added: `tfl.output.include` (section 5.2, rule 7).
   - `tfl.population` has a default per table family: the randomized set
     for the demographics table, the safety set for the other three. The
     appendix proposes the safety set for all. Reasons: the pilot CSR and
     ICH E3 section 11.2 show demographics on all randomized subjects, and
     with the safety set everywhere no M1 output would read planned
     treatment.
   - `bds.window.table` defaults to the nominal visit, not to protocol
     windows: a window table is study content, which a house standard
     cannot supply.
   - `pop.efficacy.rule` has no default, for the same reason: both
     alternatives name a study measure or a visit. It applies only to a
     design with an efficacy-evaluable population.
   - `tfl.denominator` and `tfl.pvalue.format` apply to the demographics
     table only (the two adverse event tables show percentages with a fixed
     denominator); `tfl.quantile.definition` and `tfl.decimals.rule` to
     the demographics and the vital signs table; `tfl.percent.format` to
     the three tables with percentages.
   - `demo.baseline.record`: the default is the last value on or before the
     treatment start date, by date. The appendix proposes "last before
     first dose". The rule of ADVS (`bds.baseline.rule`) looks at the time
     of the dose; so a weight timed after the dose on the first dose day is
     the baseline weight of ADSL and not the baseline of ADVS. The owner
     may want one rule for both.
   - `trt.end.source`: every alternative reads exposure records with a
     dose, as the start default does (admiral's ADSL vignette filters both
     the same way). The appendix has no such restriction.
   - `trt.date.imputation`: a partial date that is not completed is left
     out, and the treatment date is taken from the other records. It does
     not void the treatment date of the subject.
   - Three alternatives have no public source of their own
     (`unsourced_alternatives` in `standard/catalog/catalog.yaml`). Rule 5
     of section 5.2 asks for one per alternative; the gate text asks for
     one per entry, and the gate checks that.
   - `disp.status.record`: the second alternative selects by subcategory
     (DSSCAT), not by term.
   - `bds.baseline.rule`, first alternative: a value on the first dose date
     counts as before the first dose unless both times were collected and
     the value is not earlier.

8. The gate has two checks the plan does not ask for. "yamaa run" builds
   every distinct set of compiled ADaM specs on a hand-made study of three
   subjects (`specfirst.compile.tiny`), because `yamaa check` reads no data
   and passed a spec that could not run (docs/lessons.md, lesson 17). The
   ARS schema check runs three negative controls on the pinned schema. The
   compiled files and built datasets of these checks go to a new folder
   under the system's temporary folder: yamaa refuses to save a dataset on
   a Windows drive under WSL (lesson 20).

## The four open schema points of ADR-000, item 7

The owner decides these at N1. Each has a recommendation; none is applied.
On 2026-11-17 the owner took all four recommendations (see "Node N1: the
owner's answer" above); points 3 and 4 are applied by std-2 and real-3.

1. Where a `cites` edge may start. Recommendation: keep version 0 (a
   decision, an ADaM variable or an analysis). real-1 and real-3 need edges
   before the pilot has decision records. When std-2 expresses the pilot's
   gold as decision records, an imported edge whose variable a decision
   binds is re-pointed to that decision. No schema change.

2. A record in `conflict` needs no class. Recommendation: keep. Section 4.5
   says a person decides before any class is given.

3. Which records must cite (review finding N1 of base-0; std-1 owns it).
   Recommendation: one rule for every class. A record with the status
   `stated` or `default` carries at least one citation.
   - `document_rule` cites the protocol or the SAP; `house_default` cites
     the house standard. Both as now.
   - `study_input` with a value cites the person's answer: document
     `answers`, the anchor is the ID of the ask (section 11.3).
   - `gold_quirk` cites the place in the reference where the rule shows:
     document `csr` or `adam`. Its status is `stated`. The proof stays in
     `gold/exceptions.yaml`; the citation only says where to look.
   - `no_gold` records have no value, so the rule does not reach them.
   This narrows the version 0 rule and closes the gap of finding N1. It is
   a change of `decision-record.schema.json` and of two of its examples;
   std-2 would make it once the owner agrees.

4. A `decides` edge to a layout element. Recommendation: add the prefix
   `layout:` to element IDs, written `layout:<unit>/<part>`. The compiler
   already records such IDs in `compile.json` under `layout`, apart from
   `binds`, because version 0 would refuse them. real-3 owns the final form
   of the IDs with ADR-003.

## Consequences

- gen-1 can start from this draft: entries, alternatives, slots and probe
  recipes are in place. A change the owner asks for at N1 changes the
  catalog version, not its shape.
- std-2 needs real-3: it aligns the layout templates, expresses the pilot's
  gold as decision records and checks the fragments by result.
- A decision can be compiled into files that no output reads (for example
  `pop.efficacy.rule` when no table uses the efficacy-evaluable set), and
  `tfl.pvalue.format` shows only when the table compares treatments. gen-2
  must treat such a decision as not applicable to the kit, or P4 cannot
  hold for it.
- The treatment columns are data-driven. The rules "ascending dose" and
  "protocol order" are layout rules; the grid builder needs the dose and
  the protocol order of each arm from the study design.
