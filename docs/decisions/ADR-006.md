# ADR-006: CDISC CORE in the environment (gen-1a)

Status: proposed, 2026-11-17. Written by the gen session with the part
gen-1a. It changes `env/`, which every track installs from; it changes no
pin of the existing Python or R environment, no schema and no text of
PLAN.md. It stands unless the owner objects. Number ADR-003 stays reserved
for real-3.

## Context

PLAN.md checks generated SDTM with CDISC CORE (section 6.4, stage S4, and
the gate of gen-1 in section 13.5). base-0 left the installation to gen-1:
"gen-1 adds it to the environment through `env/requirements.in` or
`env/apt-packages.txt` and `make lock`" (docs/state/gen.md).

CORE is the CDISC Rules Engine, `cdisc-org/cdisc-rules-engine`, MIT. Its
release v1.0.0 of 2026-11-03 comes in three forms:

- A package on PyPI, `cdisc-rules-engine` 1.0.0. Its own documentation
  says that it "does not include `core.py`" and needs the rules cache from
  the repository; controlled terminology and library metadata otherwise
  need a key for the CDISC Library.
- Executables built with PyInstaller, attached to the release.
- The source at the tag `v1.0.0`, commit
  `f3282a0d870bbdf57e326e9992cceea3ed0d9af5`. The repository ships the
  populated cache at that commit (`resources/cache`: rules, controlled
  terminology, library metadata), and "from source" is one of the two
  documented ways to run CORE.

## Decisions

1. CORE runs from source, at the commit of the release tag. `env/core-source.txt`
   names the repository, the tag and the commit. `env/install.sh` fetches
   exactly that commit (a shallow fetch, 27 MB over the network, 573 MB
   unpacked). The rules, the terminology and the metadata are the cache of
   that commit: no key, no account, no download at run time.

2. CORE has its own virtual environment, built from its own lock.
   `env/core-requirements.in` is the dependency list of CORE's
   `pyproject.toml` at that commit, with the same bounds, without
   `pyinstaller` (it builds the executable and is not imported).
   `env/lock.sh` resolves it into `env/core-requirements.lock` with uv, as
   it does for `env/requirements.lock`: exact versions with hashes.
   `env/requirements.lock` is unchanged, byte for byte, and so is what CI
   installs.

3. One package of the lock has no wheel: `titlecase` 2.4.1, which CORE
   imports. `env/core-sdist.txt` lists it. The install has two steps: first
   every other package with `--only-binary=:all:`, then the listed ones from
   their pinned source archives with `--no-build-isolation`, so the build
   uses the `setuptools` and `setuptools_scm` of the same lock. Both steps
   use `--require-hashes`. `setuptools_scm` is in the lock for this build
   only.

4. Both parts live in one folder named after the two pins:
   `<SPECFIRST_CORE>/<first 12 digits of the commit>-<first 12 digits of the
   SHA-256 of the lock>/venv` and `/src`. `scripts/env.sh` sets
   `SPECFIRST_CORE` to `.core` in the checkout, or to `$SPECFIRST_HOME/core`
   where the environment is outside the checkout. Checkouts with the same
   pins share one install; a changed pin gives a new folder and never
   reuses an old one.

5. `specfirst doctor` checks both parts (`specfirst.cdisccore.drift`): every
   package of the lock is installed at its version and nothing else is,
   the source is at the pinned commit, and its tree is clean, ignored files
   included. The doctor is the first check of every gate.

6. The runner (`specfirst.cdisccore.validate`) starts
   `python -B core.py validate` in a scratch folder that links CORE's
   `resources`, because CORE finds them relative to the working folder. So
   CORE writes nothing into its source tree; the gate checks the tree again
   after its runs. The runner passes a pool size of 2: CORE otherwise starts
   one worker per processor, each of which loads the rule cache.

7. The datasets go to CORE as Dataset-JSON v1.1 with a Define-XML v2.1, the
   standard SDTMIG v3.4, and the controlled terminology package that the
   Define-XML names (SDTM CT 2025-09-26, the last one that still has the
   codelists RACE and ETHNIC that SDTMIG v3.4 refers to).

## Alternatives that were not taken

- The package from PyPI in `env/requirements.in`, as the handover of base-0
  suggests. It resolves beside the existing pins without changing one of
  them (43 more packages). It was not taken for three reasons: the package
  alone cannot validate (no command line, no rules); `titlecase` has no
  wheel, so the install of the main environment and of CI would need the
  two steps of decision 3; and the engine's dependencies (dask, redis and
  the like) would sit in the environment of our own code.
- The executable of the release. It was downloaded in this session and its
  SHA-256 equalled the one GitHub publishes, but it was never run: the
  session's permission policy refused to execute a downloaded binary, and
  the files were deleted. The source form needs no such trust: it is
  Python code at a commit, run by an interpreter with locked packages.
- CORE as a pinned source of `third_party/sources.yaml`. That file is
  appendix A of PLAN.md (a test keeps them equal), so a new source would be
  a change of the plan. CORE is also an engine, not an input: it belongs in
  `env/` with the other engines.

## Consequences

- Every track: after merging `main`, run `make install` once. The doctor
  fails until CORE is installed. On a machine where another checkout has
  installed the same pins, the install finds them and only checks them.
- The first install downloads about 180 MB of wheels and the 27 MB of the
  source, and takes 573 MB and 445 MB on disk.
- CI does not install CORE and does not run it. The gate gen-1a runs it on
  the owner's machine, like the evidence tests and R.
- CORE 1.0.0 cannot execute 38 of its 562 rules for SDTMIG v3.4, and six
  rules report on any data, the public CDISC pilot datasets included.
  `src/specfirst/gen/core_findings.yaml` lists each with its reason; the
  gate accepts nothing that is not on that list (docs/reports/gen-1a.md).
  A later release of CORE needs that list read again.
- Changing the pin: edit `env/core-source.txt` and, when the dependency
  list of CORE changed, `env/core-requirements.in`; run `make lock`,
  `make install` and the gate gen-1a.

## For the owner

1. The lock `env/core-requirements.lock` was resolved on 2026-11-17 with uv
   0.13.9 on the Windows side of the owner's machine, for Linux x86_64 and
   Python 3.12 (`--python-platform x86_64-manylinux_2_39`), because WSL had
   no network that day. `env/README.md` asks for `make lock` on the
   reference platform. docs/reports/gen-1a.md says whether that was done
   before the merge and whether the file came out the same.
2. A newer release of CORE than v1.0.0 is a new pin and a new reading of
   the list of explained findings. Nothing follows the upstream by itself.
